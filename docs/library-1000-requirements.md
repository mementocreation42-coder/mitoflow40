# ライブラリ 1000ページ化 要件定義書

- 対象：Mitoflow40 ライブラリ（`app/` 配下のナレッジ系ページ群）
- 到達点：ライブラリ系URLを約270 → **1000**（長期の地平線）
- **基本思想：1ページを大切にし、徐々に積み上げていく**
- SEO方針：検索集客の最大化（ただし「量産」ではなく「良質な1ページの蓄積」で達成する）
- 作成日：2026-07-21

---

## 0. この方針の中心にある考え方

> **1000は目標（締切）ではなく、地平線（方向）である。**

各ページは、テンプレートに機械的に流し込む「在庫」ではなく、それ単体で読む価値のある1枚として作る。1000という数字は「そこまで一気に埋める」ためのものではなく、「1枚ずつ良いものを積み上げ続ければ、いずれ到達する」という方向を示すもの。

この思想が、技術・編集・SEOのすべての要件に優先する。

- **編集**：1ページ = 1つの固有の視点（歴史・細胞・ATP軸）。テンプレの穴埋めは作らない。
- **SEO**：Google の *scaled content abuse ポリシー（2024年3月）* を、リスク回避策としてではなく **そもそも量産しない** ことで根本的に回避する。良質なページの蓄積は、大量薄ページの一括公開よりはるかに安全で、長期的に強い。
- **技術**：「1枚を大切に作る」を支えるために、**1枚を追加する手間を最小化する**基盤を整える。量産のためではなく、丁寧さを持続可能にするための自動化。

## 2. 最重要の技術認識：2つの実装モデルが同居している

### データ駆動モデル（1枚の追加が軽い）
`lib/foods.ts` に1件追加すると、以下が **自動で** 増える：
- 詳細ページ・`app/sitemap.ts`・`lib/searchIndex.ts`・一覧ページ

→ **1枚を丁寧に足す作業に集中できる方式。** データ（＝中身）を書くことだけに向き合える。

### 直書きモデル（1枚の追加が重い）
1ページ追加ごとに、以下を **手動で** 実施する必要がある：
1. `app/<topic>/page.tsx` を新規作成（約250〜290行のボイラープレート）
2. `app/sitemap.ts` の `staticPages` に手動追記
3. `lib/searchIndex.ts` の `conceptPages` に手動追記
4. `app/library/map/page.tsx` の `pages` に手動追記
5. metadata / JsonLd / Breadcrumbs を個別記述

→ 96ページで既に破綻の兆候。`library/map` は「代表ページのみ」と注記、`searchIndex.ts` の `conceptPages` も実ページと乖離し始めている。**「1枚を大切に」の思想でも、この手間は中身を書く集中を削ぐ。** ボイラープレートに労力を取られ、肝心の内容が薄くなる。

### 結論
**直書きの重さを、データ駆動の軽さに寄せる。** そうすれば、書き手は「レイアウトや登録作業」ではなく「その1ページで何を伝えるか」だけに集中できる。自動化は量産のためではなく、**1枚1枚に注ぐ手間の質を上げるため**。

## 3. 到達点と、その質

### 質（最優先）
- 各ページが固有の視点を持ち、それ単体で読む価値がある
- 全ページに `uniqueAngle`（そのページならではの切り口：歴史・細胞・ATP軸）が宿る
- 既存の編集トーン（中立だが明確なPOV／歴史から問い直す／ATP・細胞軸）を保つ
- テンプレの穴埋めだけの空ページは **作らない・出さない**

### 量（結果としてついてくる）
- ライブラリ系URL：270 → 1000（地平線）
- 新規ページの100%が sitemap・横断検索・一覧・内部リンクに自動登録される
- 全ページ被内部リンク2本以上（orphanページゼロ）

> 量は目標ではなく、質の蓄積の結果。「今週何枚出したか」ではなく「今週の1枚がどれだけ良かったか」で進捗を測る。

## 4. 積み上げの方向性（SEO集客・バックログ）

以下は「一気に埋めるノルマ」ではなく、**1枚ずつ選んで作っていくための優先候補リスト**。検索需要の大きい領域から、良い題材を1つずつ拾って書き上げていく。

| 領域 | 現在 | 地平線 | 検索需要の狙い |
|---|---|---|---|
| symptoms（症状逆引き） | 16 | ~150 | 「◯◯ だるい」「◯◯ 原因」等の症状系検索 |
| foods（食材） | 31 | ~200 | 「◯◯ 栄養」「◯◯ 効果」食材検索 |
| glossary（生化学・栄養用語集）※新設 | 0 | ~130 | 用語の定義系検索 |
| conditions（不調・現代病）※新設 | 0 | ~100 | 疾患名・病態名の情報系検索 |
| supplements（サプリ成分）※新設 | 0 | ~90 | 成分名・比較検索 |
| nutrients（栄養素） | 31 | ~80 | ビタミン・ミネラル各論 |
| biomarkers（検査項目） | 52 | ~90 | 「◯◯ 数値 高い/低い」検索 |
| herbs/機能性食品・漢方 ※新設 | 0 | ~50 | 素材名検索 |
| genes / hormones / organs | 30 | ~60 | 各論の深掘り |

新設コレクションは、**その領域で最初の1枚を丁寧に作る → それを型（データ＋テンプレート）として、次の1枚を軽く足せるようにする**、という順で立ち上げる。最初の1枚がそのコレクションの品質基準になる。

## 5. 機能要件（1枚を軽く・美しく足すための基盤）

### FR-1. 共通コンテンツスキーマ
各コレクションのデータ型に必須フィールドを定義し、ビルド時に欠落を検出。

```
slug, name, en, reading?, tagline, category,
sections: { heading, body }[]   // 本文（最低3節を型で強制）
relatedSlugs: string[]          // 内部リンク（最低2件）
references: { title, url? }[]    // 出典（YMYL必須）
uniqueAngle                     // そのページ固有の視点（必須）
updatedAt
```

### FR-2. 共通ページテンプレート
現行 `app/mitochondria/page.tsx` 相当のレイアウトを**単一の再利用コンポーネント**に抽出。各詳細ページはデータのみ差し替え。書き手はレイアウトを気にせず中身に集中できる。

### FR-3. 自動レジストリ化
sitemap / searchIndex / 一覧 / library map / 関連リンクを、手書きリストではなく**データ配列から機械生成**に統一。直書きページも registry に1行足せば全系統に載る。現状の「3〜4箇所への手動追記」を撲滅し、**1枚追加 = データ1件記述**にする。

### FR-4. 内部リンクの自動生成
`relatedSlugs` と `category` から関連ブロックを自動描画。全ページ被リンク2本以上を機械保証（orphan検出をビルドに組込）。積み上げるほどページ同士が有機的につながる。

### FR-5. OGP画像の自動生成
`lib/og.tsx` を全コレクションに適用し、追加ページのOGPを動的生成（手作業ゼロ）。

### FR-6. 横断検索のスケール
現在は全件を1配列でクライアント側絞り込み。件数が増えた段階でバンドルサイズ・初期ロードを計測し、必要なら分割ロード / 軽量インデックス化。**今すぐではなく、増えてきたら対応**でよい（積み上げ方針と整合）。

## 6. 品質・編集要件

### QR-1. 薄いコンテンツを「作らない」
- 本文3節・`uniqueAngle`・`references`1件以上を型で強制
- 穴埋めだけの空ページはビルドバリデーションで弾く
- 「出せるから出す」のではなく「良いから出す」

### QR-2. 1枚ごとの固有性
- 導入文・切り口にページ固有の視点（歴史・細胞・ATP軸）を必ず宿す
- 同一構文の反復を避ける（結果として scaled-content 判定リスクも消える）

### QR-3. E-E-A-T / 医療免責（YMYL）
- 著者情報・出典・免責表示を全ページ必須
- symptoms / conditions は断定を避けるトーン規定

### QR-4. 重複・カニバリ回避
- 類似スラッグ（gut-health / gut-troubles / microbiome 等）の canonical と棲み分け
- symptoms（体感の逆引き）と conditions（病態）の境界を明確化

---

## 7. 非機能・運用要件

- **NFR-1 ビルド**：ページ増加に伴い `next build` 時間・メモリを継続計測。閾値超過時に ISR 移行を判断（積み上げ途中で無理なく切り替え）。
- **NFR-2 制作フロー**：1件 = 1データ入力に単純化。書く → 編集レビュー → バリデーション通過 → マージ。**1枚ずつ確実に。**
- **NFR-3 計測**：進捗は「累計ページ数」ではなく **「公開済みページのインデックス率・被リンク・滞在」の質** で測る。Search Console の「クロール済み-未インデックス」率を監視。
- **NFR-4 リリース**：一括公開しない。**1枚（または数枚）ずつ公開し、その都度インデックスと反応を確認**してから次へ。これが積み上げ方針の実装形。

---

## 8. 進め方（フェーズではなく、順序）

「◯ヶ月で◯◯枚」という計画ではなく、**土台 → 1枚目 → 型化 → 蓄積**という順序で進める。

1. **土台を整える**：共通テンプレート抽出 + registry自動生成へのリファクタ。既存96直書きページも巻き取る。→ これ以降、1枚の追加が軽くなる。
2. **各領域の1枚目を丁寧に作る**：新設コレクション（glossary / conditions / supplements / herbs）の最初の1枚を、品質基準となるレベルで書き上げる。
3. **型として横に広げる**：1枚目を型に、次の1枚を軽く足せるようにする。以降は「良い題材を選んで1枚ずつ」。
4. **蓄積を続ける**：既存コレクション（symptoms / foods / nutrients）も同じリズムで1枚ずつ積む。内部リンク密度は積み上げとともに自然に高まる。

## 9. リスクと対策

| リスク | 対策 |
|---|---|
| 薄いページの混入 | `uniqueAngle`必須 + ビルドバリデーション + 「良いから出す」原則 |
| ボイラープレートに労力を取られ中身が薄くなる | 自動レジストリ化（FR-3）で書き手を中身に集中させる |
| ビルド時間/メモリ超過 | 増加に応じて ISR 移行（NFR-1） |
| orphanページ | relatedSlugs必須 + orphan検出（FR-4） |
| コレクション間カニバリ | canonical・棲み分け（QR-4） |

## 11. 進捗メモ（2026-08-21）

**土台→1枚目→型化 の「1枚目」と「型」ができた。**

- **conditions コレクション新設**：`lib/conditions.ts`（型＋ビルド時バリデーション：本文3節・uniqueAngle・出典1件・関連2件・リンク切れを `import` 時に検出して落とす）→ `/conditions`・`/conditions/[slug]`・OG画像・横断検索・sitemap・ライブラリ索引/マップに自動反映。**1枚追加 = データ1件**になった。
- **最初の1枚**：`/conditions/iron-deficiency`（鉄欠乏・隠れ貧血）。セクション構成＝定義 → サイン → EVIDENCE/HISTORY/CORE/NEUTRAL バッジ付き本文 → 血液検査 → 栄養素・食材 → 症状逆引き → 打ち手 → 受診の目安 → 解析導線 → 出典。これを品質基準にする。
- **直書きの病態ページ（15本）**は `/conditions` 一覧に「未移行」として載せてある（`LEGACY_CONDITION_PATHS`）。1枚ずつ conditions に巻き取ったらリストから外す。
- **自動関連ブロック**：`lib/related.ts` が全コレクションを逆引きし、`RelatedBlock` で biomarkers / nutrients / symptoms / foods の各ページ末尾に「次に読む」を描画（1グループ最大8件）。conditions を1枚足すと、参照先の検査項目・症状・栄養素・食材ページに自動で被リンクが生える。
- **/check → ライブラリ誘導**：結果画面の弱い軸ごとに5ページを提示（`AXIS_PAGES`）。
- **検査値リーダー** `/biomarkers/reader`：52項目の基準値・理想値文字列を `lib/biomarker-ranges.ts` が数値化（全項目・男女でパース成功を確認済み）。入力は localStorage のみ、送信なし。解析プランへの導線つき。
- **ライブラリ → 決済の導線**：`AnalysisCta` を conditions / biomarkers / symptoms ページに設置（→ /biomarkers/reader と /plans）。

### 次の1枚の足し方
1. `lib/conditions.ts` の配列に1件追加（`updatedAt` を忘れずに）
2. `npm run build` または `npx tsc` でバリデーション通過を確認（落ちたらメッセージの通りに直す）
3. 既存の直書きページを巻き取る場合は、`app/<topic>/page.tsx` を `redirect('/conditions/<slug>')` に差し替え、`lib/pages.ts` の該当行と `LEGACY_CONDITION_PATHS` から外す
4. 公開後、Search Console でインデックスを確認してから次へ（NFR-4）

### 候補（検索需要と既存データの接続から）
甲状腺機能低下（TSH/FT3/FT4・冷え・抜け毛）／ビタミンD不足／インスリン抵抗性（直書きの巻き取り）／脂肪肝（巻き取り）／隠れ炎症（hs-CRP）／亜鉛欠乏（味覚・肌・免疫）
